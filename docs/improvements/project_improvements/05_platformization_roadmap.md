# AI 测试自动化平台通用化改造路线图

## 1. 背景与目标

当前项目已经具备一条可运行的主流程：

`需求分析 -> 用例生成 -> 用例评审 -> 脚本生成 -> 执行用例 -> 生成 Allure 报告`

但现阶段更接近“可运行的原型”或“若干场景可验证的 POC”，还不能认为已经达成“通用测试平台”的目标。

本路线图的目标是把项目从“针对部分场景可跑通”升级为“面向不同类型 Web 需求、可重复执行、可解释失败原因、可持续扩展”的通用平台。

最终目标不是让平台只适配某一个页面或某一类需求，而是具备稳定支持以下能力：

- 通用需求分析
- 通用测试用例生成
- 通用测试用例评审
- 通用执行策略选择
- 通用测试报告产出

## 2. 当前状态判断

### 2.1 已经具备的基础能力

- 已经具备完整的主流程骨架
- 已经引入 LangGraph 作为工作流编排能力
- 已经引入 Pydantic 作为结构化模型约束
- 已经具备 Midscene + Playwright 混合执行能力
- 已经具备 Allure 报告导出能力
- 已经补充了结构化输出失败诊断与日志能力

### 2.2 当前主要短板

当前最明显的问题不是“主流程完全跑不起来”，而是“主流程对不同需求类型的通用性不足”。

主要体现在：

- 测试步骤到执行脚本的转换仍然偏场景化
- 上游 Agent 生成的步骤可执行性约束不够强
- 执行层的 Midscene / Playwright 分工还未正式抽象成统一策略
- 失败原因虽然能暴露出来，但还没有形成平台级分类体系
- 回归验证样本仍然偏少，跨页面类型覆盖不足

### 2.3 当前阶段结论

当前项目已经进入：

`可以运行完整流程，但距离“通用平台”仍需要一轮系统化抽象`

也就是说，现在的重点不应该继续围绕单一需求打补丁，而应该把“需求 -> 用例 -> 动作 -> 执行 -> 报告”这条链路抽象成稳定的通用框架。

## 3. 平台化改造总原则

在后续改造中，建议坚持以下原则：

### 3.1 不追求“全部交给 Midscene”

平台的目标不是把所有步骤都强行交给 Midscene，而是建立合理的混合策略：

- 确定性动作使用 Playwright
- 语义理解、视觉判断、复杂页面理解使用 Midscene

这不是降级，而是平台级能力划分。

### 3.2 不再直接从自然语言步骤生成页面特化脚本

中间必须引入一层统一动作语义层，即通用动作 IR。

### 3.3 上游输出必须对执行层负责

需求分析、测试用例生成、评审，不应只产出“看起来合理”的内容，而应该产出“可执行”的内容。

### 3.4 报告系统必须解释失败原因

平台的价值不只是告诉用户“失败了”，还要说明：

- 为什么失败
- 失败在哪一层
- 是需求问题、用例问题、模型问题、执行问题，还是环境问题

## 4. 改造分阶段路线

---

## 阶段一：主流程稳定化

### 4.1 目标

先把主流程稳定下来，确保每次运行都能：

- 产生可读结果
- 产生可解释失败原因
- 正确生成报告

### 4.2 重点工作

#### 任务 1：固化执行策略层

把当前执行层的经验性逻辑抽象为正式策略：

- 哪些动作必须走 Playwright
- 哪些动作必须走 Midscene
- 哪些动作允许 Midscene 失败后降级
- 哪些动作不能降级

建议新增明确的策略模块，而不是把规则散在脚本生成器中。

#### 任务 2：完善失败分类

统一定义失败类型：

- 结构化输出失败
- 模型额度不足
- 模型兼容性问题
- 模型响应格式错误
- 元素定位失败
- 页面截图/上下文采集超时
- 断言失败
- 环境错误
- 报告生成错误

这些类型应统一在执行结果和 Allure 中展示。

#### 任务 3：增强报告解释性

Allure 报告和执行结果 JSON 中应明确包含：

- 原始测试步骤
- 转换后的动作步骤
- 实际执行方式（Midscene / Playwright）
- 失败发生的步骤编号
- 原始异常
- fallback 是否发生

#### 任务 4：建立标准验收样本集

至少固定以下 3 类基准场景：

- 表单输入类
- 点击跳转类
- 结果页断言类

这些场景必须能够稳定通过，或在失败时给出清晰分类。

### 4.3 验收标准

阶段一完成时，应满足：

- `main_v2.py` 能稳定跑完
- Allure 报告能稳定生成
- 失败结果能明确归因
- 小规模标准样本集可重复执行

---

## 阶段二：动作模型通用化

### 5.1 目标

把“自然语言测试步骤”转换成“统一动作模型”，摆脱页面级硬编码。

### 5.2 核心思想

在脚本生成之前，增加一层通用动作 IR（Intermediate Representation）。

示例动作类型：

- `open_page`
- `wait_page_ready`
- `find_element`
- `input_text`
- `clear_field`
- `click_element`
- `assert_visible`
- `assert_enabled`
- `assert_text`
- `assert_url_changed`
- `assert_list_present`
- `assert_empty_state`
- `assert_no_error`
- `observe_visual_state`

### 5.3 重点工作

#### 任务 1：定义动作 IR Schema

建议每个动作至少包含：

- `action_type`
- `target`
- `input`
- `expected`
- `execution_mode`
- `can_fallback`
- `metadata`

#### 任务 2：上游 Agent 输出对齐到 IR

需求分析、测试用例生成、评审阶段应逐步引导输出：

- 操作意图
- 目标对象
- 输入数据
- 预期结果

避免继续生成过于模糊的自然语言步骤，例如：

- “观察页面行为”
- “验证操作成功”
- “页面正常显示”

#### 任务 3：评审增加可执行性校验

评审器不只负责打分，还要明确指出：

- 步骤是否缺 target
- 预期是否过于模糊
- 是否依赖未声明的前置条件
- 是否缺少结果判断标准

#### 任务 4：脚本生成器改为 IR -> Script

脚本生成器不再直接消费自然语言步骤，而是消费动作 IR。

### 5.4 验收标准

阶段二完成时，应满足：

- 不同需求类型可映射到统一动作模型
- 执行层不再依赖页面名称或单页面关键词特判
- 新需求接入时，主要新增的是动作模板，而不是页面补丁

---

## 阶段三：多场景回归体系

### 6.1 目标

验证平台对不同页面类型和业务场景的适应能力。

### 6.2 建议补充的标准场景

至少建立以下 5 类场景基线：

- 登录 / 鉴权类
- 表单填写类
- 列表查询类
- 弹窗确认类
- 结果页断言类

建议每类都准备：

- 一份需求文档
- 一组标准用例
- 一套预期执行结果

### 6.3 重点工作

#### 任务 1：集成测试矩阵

在 `tests/integration` 中引入多场景矩阵测试，不只测主流程跑通，还要测：

- 动作 IR 是否正确
- 执行策略是否合理
- 报告结果是否符合预期

#### 任务 2：回归验收标准

每次改动后至少运行：

- 核心冒烟场景
- 一个视觉依赖场景
- 一个空状态或异常流场景

#### 任务 3：建立失败样本库

将典型失败保留下来，用于回归：

- 429 配额问题
- 模型响应不规范
- 页面截图超时
- 元素无法定位
- 断言不稳定

### 6.4 验收标准

阶段三完成时，应满足：

- 平台对多类页面具备可重复执行能力
- 同类问题不再反复回归
- 新需求接入时，失败定位明显加快

---

## 阶段四：平台配置化与扩展能力

### 7.1 目标

让平台从“项目工程”升级为“可配置、可扩展的平台能力”。

### 7.2 重点工作

#### 任务 1：模型路由配置化

拆分模型职责：

- 文本结构化模型
- 测试用例生成模型
- 评审模型
- 视觉执行模型

每个模型的用途、Base URL、Key、Model Name 都应在配置中统一管理。

#### 任务 2：页面模板与动作模板配置化

把常见页面控件抽象成可配置模板：

- 输入框模板
- 按钮模板
- 列表模板
- 搜索结果模板
- 弹窗模板

#### 任务 3：执行策略配置化

允许不同系统设置自己的执行策略，例如：

- 更偏 Playwright
- 更偏 Midscene
- 严格禁止 fallback
- 允许弱化某些视觉断言

#### 任务 4：可观测性完善

统一沉淀以下产物：

- 原始需求
- 结构化需求
- 生成的测试用例
- 评审意见
- 动作 IR
- 最终执行脚本
- 执行日志
- 截图
- Allure 报告

### 7.3 验收标准

阶段四完成时，应满足：

- 平台接入新系统时主要依赖配置和模板扩展
- 不需要频繁改动核心代码
- 同一平台可以支持多种模型组合和多种页面类型

## 5. 当前最优先的实施顺序

建议严格按以下顺序推进：

### 第一优先级

- 固化执行策略层
- 完善失败分类
- 强化报告解释性
- 建立小规模标准验收样本

### 第二优先级

- 定义通用动作 IR
- 上游 Agent 输出对齐到 IR
- 评审器增加可执行性校验
- 脚本生成器切换为 IR 驱动

### 第三优先级

- 多场景回归矩阵
- 失败样本库
- 配置化页面模板
- 配置化模型路由

## 6. 建议的近期开发任务清单

如果按“本周可落地”的角度，建议先做下面几件事：

### 本周任务 A：执行与报告稳定化

- 把执行失败分类统一到一个枚举中
- 在执行结果 JSON 中增加失败层级字段
- 在 Allure 中展示失败分类和原始异常

### 本周任务 B：定义动作 IR 初版

- 先支持最核心的 8 到 10 个动作类型
- 为每个动作类型定义执行模式
- 让脚本生成器先消费 IR，而不是自然语言步骤

### 本周任务 C：增强评审可执行性

- 增加“目标对象缺失”检查
- 增加“预期结果模糊”检查
- 增加“前置条件不足”检查

### 本周任务 D：建立平台验收样本

- 表单输入
- 搜索跳转
- 空状态
- 结果页断言

## 7. 最终判断

当前项目已经具备平台雏形，但还未达到“通用平台完成态”。

要实现最终目标，最关键的一步不是继续为单个需求写规则，而是：

`建立自然语言测试步骤 -> 通用动作 IR -> 混合执行策略 -> 可解释报告 的统一链路`

只要这条链路建立起来，后面的需求变化就会变成“扩展动作模板和场景回归”，而不是“不断为新页面打补丁”。
