 # AI自动化测试平台 - 面试问答指南

## 一、项目整体架构

### Q1: 简单介绍一下这个项目？

**回答要点：**
- 背景：测试用例编写效率低、维护成本高
- 解决方案：基于 LLM 的端到端自动化平台
- 核心流程：需求文档 → 需求分析 → 策略规划 → 用例生成 → 评审迭代 → 脚本规划 → UI执行
- 技术栈：LangGraph + LangChain + Pydantic + Midscene + Playwright

**参考回答：**

这是一个基于大语言模型的智能测试平台，核心目标是实现从需求文档到可执行测试脚本的端到端自动化。

整个流程分为6个阶段：首先是需求分析，把Markdown需求文档解析成结构化的需求列表；然后是策略规划，根据需求的重要程度和风险等级，自动计算测试用例预算和覆盖维度；接着生成测试用例，并通过评审Agent进行质量检查，评审不通过会自动迭代重试；最后是脚本规划和UI执行，生成可运行的Playwright脚本并执行。

技术栈方面，我用LangGraph编排整个工作流，Pydantic做数据模型，Midscene做AI视觉定位，最终输出Allure测试报告。

---

### Q2: 为什么选择LangGraph而不是直接调用LLM API？

**回答要点：**
- 工作流可编排：节点、边、条件分支
- 状态可追踪：每个节点的状态都保存在AgentState中
- 支持迭代：评审不通过可以回退重试
- 可扩展：方便新增节点

**参考回答：**

主要有三个原因：

第一是**工作流编排能力**。LangGraph可以定义节点和边，支持条件分支。比如评审节点之后，根据评审结果决定是继续生成脚本还是回退重新生成用例，这种逻辑用LangGraph的conditional_edges很容易实现。

第二是**状态管理**。LangGraph的StateGraph会自动维护一个AgentState，每个节点的输出都会保存下来。比如需求分析的结果会被策略规划节点使用，策略规划的结果会被用例生成节点使用，这种数据流转很清晰。

第三是**可扩展性**。如果我想新增一个节点，比如加一个"用例优化"节点，只需要定义节点函数、添加到图中、连好边就行了，不影响其他节点。

如果直接调LLM API，这些逻辑都要自己手写，代码会很乱。

---

### Q3: 整个流程的数据流转是怎样的？

**回答要点：**
- AgentState作为全局状态
- 每个节点读取上游数据、写入下游数据
- 最终输出8类结构化产物

**参考回答：**

整个流程的数据流转是通过AgentState这个全局状态对象来实现的。

需求分析节点读取原始需求文档，输出requirements列表；策略规划节点读取requirements，输出test_strategy；用例生成节点读取test_strategy，输出test_cases；评审节点读取test_cases，输出review_score和review_passed；如果评审不通过，会回退到用例生成节点重新生成。

脚本规划节点读取test_cases，输出script_plans；执行节点读取script_plans，运行生成的脚本，输出execution_results。

最终会输出8类JSON文件：requirements.json、test_strategy.json、test_cases.json、review.json、script_plan.json、execution.json、run_summary.json、run_manifest.json。

## 二、LangGraph工作流

### Q4: 你提到了6个节点，能具体说说每个节点做什么吗？

**回答要点：**
- 需求分析：解析Markdown，提取结构化需求
- 策略规划：计算FocusPoint、用例预算、覆盖维度
- 用例生成：根据策略生成测试用例
- 评审迭代：检查用例质量，不通过则重试
- 脚本规划：决定每步用native还是AI执行
- 执行：运行脚本，生成报告

**参考回答：**

**需求分析节点**：读取Markdown需求文档，调用LLM提取结构化的需求列表，包括需求ID、标题、描述、验收标准等。

**策略规划节点**：这是我自己设计的核心模块。它会分析每个需求的验收标准，按照critical/major/normal/light四级关注度分配测试资源，计算每个需求应该生成多少个测试用例，覆盖哪些维度（happy_path、negative、boundary等）。

**用例生成节点**：根据策略规划的结果，调用LLM生成具体的测试用例，包括步骤、预期结果、标签等。

**评审节点**：对生成的用例进行质量检查，包括步骤完整性、预期结果可验证性、与需求的对应关系等。输出一个0-100的评分，低于阈值就标记为不通过。

**脚本规划节点**：这是另一个核心模块。它会分析每个测试步骤，决定用playwright_native、midscene_ai还是mixed模式执行，并生成结构化的执行计划。

**执行节点**：根据脚本计划生成TypeScript测试脚本，调用Playwright执行，最后生成Allure报告。

---

### Q5: 评审不通过时如何实现迭代重试？

**回答要点：**
- conditional_edges条件分支
- iteration_count计数器
- max_iterations上限（默认2次）

**参考回答：**

这是通过LangGraph的条件边实现的。

评审节点输出review_passed和review_score之后，有一个routing函数判断是否需要重新生成。如果review_passed为False且iteration_count < max_iterations，就路由到increment_iteration节点，计数器加1，然后跳回用例生成节点重新生成。

如果review_passed为True，或者iteration_count已经达到上限，就继续往下走到脚本规划节点。

代码大概是这样：

```python
workflow.add_conditional_edges(
    "review_test_cases",
    should_regenerate,
    {
        "regenerate": "increment_iteration",
        "end": "plan_script_generation",
    },
)
```

max_iterations默认是2次，避免无限循环。

### Q6: 如果LLM输出格式不对怎么办？

**回答要点：**
- Pydantic强校验
- 重试机制
- 降级处理（fallback）

**参考回答：**

这个问题很重要，LLM的输出确实不稳定。我用了三层保障：

**第一层是Pydantic强校验**。我定义了完整的数据模型，比如RequirementAnalysisResult、TestStrategyPlan、ScriptExecutionPlan等。LLM的输出会先经过model_validate校验，如果字段缺失或类型不对，会抛出ValidationError。

**第二层是重试机制**。如果校验失败，我会把错误信息反馈给LLM，让它重新生成。最多重试2次。

**第三层是降级处理**。如果重试还是失败，会使用一个预定义的fallback模板。比如需求分析失败，会生成一个默认的需求结构；脚本规划失败，会使用deterministic_baseline作为基线计划。

这样即使LLM输出异常，整个流程也不会中断。

## 三、评审机制

### Q7: 你是如何评判生成的测试用例的？

**回答要点：**
- 五维度评分：completeness、coverage、reasonability、independence、clarity
- 可执行性评分：检查步骤是否可自动化执行
- 通过条件：score >= 60 且所有需求有覆盖
- 评论类型：error、warning、suggestion、no_coverage

**参考回答：**

我设计了一个多维度评审机制，主要包括两部分：

**第一部分是五维度质量评分**，每个维度0-20分，总分100分：

- **completeness（完整性）**：用例是否覆盖所有验收标准，步骤是否完整
- **coverage（覆盖率）**：是否覆盖happy_path、negative、boundary等场景
- **reasonability（合理性）**：步骤逻辑是否合理，预期结果是否正确
- **independence（独立性）**：用例是否独立，不依赖其他用例的执行结果
- **clarity（清晰度）**：描述是否清晰，没有歧义

**第二部分是可执行性评分**，也是0-20分，但不计入总分。主要检查：
- 步骤是否有明确的操作目标（如"点击登录按钮"而不是"操作按钮"）
- 预期结果是否可验证（如"显示登录成功"而不是"正常"）
- 是否有隐藏的前置依赖（如"在上一步的基础上"）
- 步骤是否难以映射到UI操作

评审通过的条件是：**总分 >= 60 且每个需求都有对应的测试用例**。如果某个需求没有生成用例，会直接标记为不通过。

---

### Q8: 评审不通过时会返回什么信息？

**回答要点：**
- ReviewComment：评论类型、严重程度、具体问题
- suggestions：改进建议列表
- executability_findings：可执行性问题列表

**参考回答：**

评审不通过时会返回三类信息：

**ReviewComment列表**：每条评论包含type（error/warning/suggestion）、severity（high/medium/low）、message（具体问题描述）。比如：

```json
{
  "type": "suggestion",
  "severity": "medium",
  "message": "Add a boundary case for an empty password."
}
```

**suggestions列表**：给用例生成Agent的改进建议，比如"Add one negative case for empty password."

**executability_findings列表**：可执行性问题，比如"Expected result wording is vague in two steps."

这些信息会传递给用例生成节点，作为下一轮迭代的参考。

## 四、FocusPoint策略模型

### Q9: FocusPoint策略模型是什么？为什么要设计它？

**回答要点：**
- 问题：不同需求的重要程度不同，用例数量如何分配？
- 解决方案：按关注度分级，自动计算用例预算
- 四级：critical/major/normal/light
- 覆盖维度：happy_path、negative、boundary、exception等

**参考回答：**

这个模型解决的是一个实际问题：不同需求的重要程度不同，应该生成多少个测试用例？全部生成happy_path还是也要覆盖异常场景？

我的设计思路是：每个验收标准（acceptance criteria）对应一个FocusPoint，根据业务价值和风险等级，分配critical/major/normal/light四个关注度级别。

- **critical**：核心功能、涉及资金/安全，case_weight=3，建议生成3个用例，覆盖happy_path+negative+exception
- **major**：重要功能，case_weight=2，建议生成2个用例，覆盖happy_path+negative
- **normal**：常规功能，case_weight=1，建议生成1个用例，覆盖happy_path
- **light**：辅助功能，case_weight=1，建议生成1个用例

这样策略规划节点输出的test_strategy就包含了每个需求应该生成多少个用例、覆盖哪些维度，用例生成节点就可以按这个策略来生成。

---

### Q10: FocusPoint的级别是如何确定的？

**回答要点：**
- LLM分析验收标准
- 考虑因素：业务价值、风险等级、用户影响
- 也可以手动配置

**参考回答：**

有两种方式：

**自动分析**：策略规划节点会调用LLM，分析每个验收标准的业务价值和风险等级。比如涉及支付、登录、权限的功能，会被标记为critical；涉及表单验证的功能，会被标记为major；纯展示类功能，会被标记为normal或light。

**手动配置**：如果用户在需求文档中明确标注了优先级，比如"【P0】登录功能"，会优先使用用户指定的级别。

实际运行中，大部分情况是自动分析的，因为需求文档通常不会写这么细。

## 五、混合执行策略

### Q11: 三种执行模式（native/ai/mixed）有什么区别？

**回答要点：**
- playwright_native：确定性高，适合高风险操作
- midscene_ai：语义理解强，适合动态元素
- mixed：结合两者优势

**参考回答：**

**playwright_native**：直接使用Playwright的API，比如page.click()、page.fill()。优点是确定性高、执行快、容易调试；缺点是依赖选择器，UI变化时需要维护。

**midscene_ai**：使用Midscene的AI视觉定位，通过自然语言描述操作元素，比如"点击登录按钮"。优点是不需要维护选择器，UI变化时适应性强；缺点是执行慢、成本高、不确定性略高。

**mixed**：结合两者优势。比如登录场景，输入用户名密码用native确保确定性，验证登录成功用AI识别"LianLian"标志。

---

### Q12: 如何决定每个步骤用哪种模式？

**回答要点：**
- 风险等级：高风险操作强制native
- 操作类型：输入、点击优先native，验证优先AI
- 场景类型：login_only场景默认native_first

**参考回答：**

这是脚本规划节点的核心逻辑，我设计了一套规则：

**按风险等级**：
- 高风险操作（登录、支付、权限变更）强制使用native或mixed，确保确定性
- 常规操作可以使用AI

**按操作类型**：
- 输入、点击等操作优先native，因为选择器通常稳定
- 验证、断言优先AI，因为需要语义理解

**按场景类型**：
- login_only场景默认native_first策略，因为涉及凭证安全
- generic场景可以使用hybrid_balanced策略

最终每个步骤都会输出preferred_executor字段，脚本生成时会根据这个字段决定如何执行。

---

### Q13: 为什么要设计mixed模式？直接用AI不行吗？

**回答要点：**
- AI不确定性：可能误操作
- 安全考虑：高风险操作不能交给AI
- 成本考虑：AI调用有成本

**参考回答：**

直接用AI有几个问题：

**不确定性**：AI可能会误判，比如把"取消"按钮当成"确认"按钮点击，导致测试结果不可预期。

**安全考虑**：登录场景涉及凭证输入，如果交给AI，可能会输入错误或泄露敏感信息。

**成本考虑**：AI调用有成本，每个步骤都调用AI会增加执行时间和费用。

所以mixed模式是一个平衡：高风险操作用native确保安全，语义验证用AI提升准确性。

## 六、安全约束设计

### Q14: login_only场景的安全约束是如何设计的？

**回答要点：**
- 运行时凭证注入：不硬编码密码
- 禁止越界操作：登录后不能乱点
- success_signal断言：检测成功标志后立即停止

**参考回答：**

login_only是一个受限场景，我设计了三重安全约束：

**运行时凭证注入**：用户名密码不硬编码在脚本里，而是从环境变量读取。需求文档可以写占位符`identifier_env: LOGIN_USERNAME`，运行时从.env文件注入实际值。这样脚本可以提交到Git，不会泄露凭证。

**禁止越界操作**：定义了forbidden_actions列表，包括menu_click、navigation_after_login、logout、profile_edit等。脚本生成时会检查，确保登录成功后不会执行额外操作。

**success_signal断言**：登录成功的判断不是靠URL或状态码，而是检测页面上的成功标志（比如"LianLian"文字或Logo）。检测到成功标志后立即停止，不会继续执行其他操作。

---

### Q15: 如果登录需要验证码怎么办？

**回答要点：**
- manual_wait模式：等待用户手动输入
- 不绕过安全机制
- 超时机制

**参考回答：**

我设计了manual_wait模式。当检测到需要验证码时，脚本会暂停，等待用户手动输入验证码，然后继续执行。

这个设计的原则是**不绕过安全机制**。验证码、MFA等安全验证，自动化脚本不应该尝试绕过，而是等待人工处理。

代码中设置了manual_wait_timeout_ms，默认180秒。如果超时，会标记为失败并记录原因。

## 七、Midscene AI视觉定位

### Q16: Midscene是如何工作的？

**回答要点：**
- 自然语言描述元素
- AI视觉定位
- 降低选择器维护成本

**参考回答：**

Midscene是一个AI驱动的UI自动化工具，核心能力是通过自然语言描述来定位和操作元素。

传统方式需要写选择器，比如`page.locator('#login-btn')`。如果前端改了ID，选择器就失效了。

Midscene的方式是直接描述意图，比如`aiAction('点击登录按钮')`。它会通过AI理解页面内容，找到符合条件的元素并执行操作。

我项目中集成了Midscene的Playwright fixture，生成的脚本可以这样写：

```typescript
await aiAction('点击提交按钮');
await aiAssert('页面显示"操作成功"');
```

---

### Q17: Midscene相比传统选择器有什么优缺点？

**回答要点：**
- 优点：维护成本低、适应UI变化
- 缺点：执行慢、成本高、不确定性略高

**参考回答：**

**优点**：
- 维护成本低：UI变化时不需要修改选择器
- 语义化：测试代码更易读
- 适应性强：能处理动态生成的元素

**缺点**：
- 执行慢：每次操作都要调用AI模型
- 成本高：API调用有费用
- 不确定性：AI可能误判，需要设计fallback

所以我的策略是混合使用：高风险操作用传统选择器确保确定性，验证断言用AI提升适应性。

## 八、Pydantic数据模型

### Q18: 你用Pydantic构建了哪些数据模型？

**回答要点：**
- Requirement：需求模型
- TestCase：测试用例模型
- ReviewResult：评审结果模型
- ScriptExecutionPlan：脚本执行计划模型
- TestStrategyPlan：测试策略模型

**参考回答：**

我定义了完整的数据模型层，主要包括：

**需求相关**：RequirementAnalysisResult、Requirement

**策略相关**：TestStrategyPlan、RequirementStrategy、FocusPointStrategy

**用例相关**：TestCase、TestCaseStep

**评审相关**：ReviewResult

**脚本相关**：ScriptExecutionPlan、ScenarioPlan、ScriptStepPlan

**执行相关**：ExecutionResult、FailureAnalysis

每个模型都用Pydantic V2定义，包括字段类型、校验规则、默认值等。比如FocusPointStrategy的case_weight字段，限制在1-3之间：

```python
case_weight: int = Field(ge=1, le=3)
```

---

### Q19: Pydantic V2相比V1有什么优势？

**回答要点：**
- 性能提升：Rust实现
- model_validator：更灵活的校验
- Field约束：ge、le、min_length等

**参考回答：**

Pydantic V2主要优势：

**性能提升**：核心用Rust重写，校验速度快5-10倍。

**更灵活的校验**：V2的model_validator支持mode="before"和mode="after"，可以在解析前后进行自定义校验。比如TestStrategyPlan中，我用了model_validator自动对齐total_suggested_case_budget：

```python
@model_validator(mode="after")
def align_total_budget(self) -> "TestStrategyPlan":
    actual_budget = sum(item.suggested_case_budget for item in self.requirement_strategies)
    if self.total_suggested_case_budget != actual_budget:
        self.total_suggested_case_budget = actual_budget
    return self
```

**更丰富的Field约束**：ge、le、min_length、max_length、pattern等，可以在定义字段时就声明约束条件。

## 九、项目成果与反思

### Q20: 这个项目最大的技术难点是什么？

**回答要点：**
- LLM输出不稳定
- 多Agent协作的状态管理
- 执行策略的设计

**参考回答：**

我认为有三个主要难点：

**第一是LLM输出不稳定**。有时候LLM返回的JSON格式不对，或者字段缺失。我通过Pydantic强校验+重试机制+降级处理解决了这个问题。

**第二是多Agent协作的状态管理**。6个节点之间的数据流转很复杂，哪个节点需要哪些数据、输出哪些数据，需要仔细设计。我用AgentState作为全局状态，每个节点只读写自己需要的字段，保持职责清晰。

**第三是执行策略的设计**。什么时候用native、什么时候用AI、什么时候用mixed，需要考虑风险、成本、确定性等多个因素。我设计了一套规则引擎，根据场景类型、操作类型、风险等级自动决策。

### Q21: 如果让你重新设计这个项目，会做哪些改进？

**回答要点：**
- 增加Web界面
- 支持更多场景
- 优化LLM调用成本
- 增加用例库

**参考回答：**

如果重新设计，我会考虑：

**增加Web界面**：目前是CLI工具，用户需要写Markdown文件。如果有Web界面，用户可以直接在页面上输入需求，查看生成的用例和报告。

**支持更多场景**：目前主要支持login_only和generic场景，可以扩展到表单验证、列表搜索、支付流程等更多场景。

**优化LLM调用成本**：目前每个节点都会调用LLM，可以考虑缓存中间结果，或者用小模型处理简单任务。

**增加用例库**：生成的用例可以存储起来，形成用例库，后续可以复用或作为few-shot示例。
